Agentic retrieval · late interaction vs grep · Magic: The Gathering

Does an agent with grep need a search engine?

I built an MCP server that gives an AI agent semantic search over every Magic: The Gathering card, for building Commander decks. Then I tried to show it was unnecessary: the same agent with nothing but grep, and the same agent reading every card. Given the same instructions, search finds more of the right cards with fewer tokens. Grep only catches up when its prompt describes the file, and then it costs twice as much.

Kasper Rømer Grøntved15 October 2026≈ 13 min Agent: Claude Sonnet 5.5 in Claude Code

An agent that knows Magic still picks cards from memory. Ask it for cards for a deck and it answers from what it remembers. That works for famous cards and fails in three predictable ways. It breaks deck rules: without tools, 13% of its suggested adds were outside the commander's colours, not legal, or already in the deck. It reaches for the most-played cards rather than the ones that do the job in this deck. And cards printed or reworded after training are invisible to it. A search tool over the official card data can fix all three, but only if the agent uses it, and only if it beats what the agent can already do with plain text tools. That second condition is the one this post is about.

01Every card, in its official wording

Everything here runs on Scryfall's Oracle cards file. Scryfall is the community's card database and publishes a fresh copy every day. The Oracle file has one entry per distinct card, whatever the printing, with the card's current official rules text: the Oracle text Wizards of the Coast keeps up to date. It can differ from the printed card. Older printings of Lightning Bolt say target creature or player; the Oracle text says any target. Each entry also carries the mana cost, type line, colour identity and legality in every format, and Scryfall's Tagger project adds community labels for what cards do; the tools show them as roles. This is one card as it sits in the card file that mLateOn reads and grep searches, one line for the name and cost, one for the type, then the rules text:

The simplest design would skip search altogether and give the agent every card to read. I tried that first.

Reading everything gave slightly better answers than search on a 12-task sample, not significantly so. The full 113 tasks would have read about 302M tokens, so I stopped there. Reading everything is a ceiling, not a design. The agent needs a way to find cards: a search engine, or at least grep.

02Search against no search infrastructure

The same agent ran 113 card-finding tasks three ways. Each task is a request: a deck need, a card with given attributes (a 1-mana red burn instant), or a specific card described in other words. The agent may make up to five tool calls and returns a ranked list of up to 20 cards. Section 4 describes how the tasks are built and graded.

  • Search: the mtg-search search tool, with minimal instructions: the request, the call budget and the answer format, and nothing on how to search.
  • Grep, same prompt: a regular expression over the plain card text, with no ranking and no filters, and the same minimal instructions as search.
  • Grep, tuned prompt: the identical grep tool, with a prompt I wrote after a first test run. It shows how a card is laid out in the file, explains how matching works, and adds general search advice and an example pattern. The only difference between the two grep runs is the prompt.

The relevance gap is almost all on card attributes. A card's mana cost, type line and rules text sit on separate lines of the file, and without a description of the layout grep guessed it wrong: it wrote patterns that expect the cost, the card type and the rules text on one line, and 29% of its calls matched nothing. When it gave up, it fell back to listing card names from memory. On deck needs, whose rules-text phrases sit on one line, the two stay close. Search does not have this problem because it has filters for colour, type and mana value, and because it ranks: a vague query still returns the ten best cards rather than nothing.

Search needed no prompt tuning. Its first prompt, never tuned, gives the same results as the minimal one: 98.5% against 98.1% relevant cards in the top 10. Grep needed a prompt that is, in effect, documentation of the file, and it still paid for it in tokens.

03Choosing the engine

Before any agent ran, I compared search engines directly on a benchmark of 363 queries with known answers, no agent and no prompt involved. The score is nDCG@10 on a 0 to 100 scale, where 100 means the correct cards fill the top 10, best first. The winner was mLateOn, a late-interaction model: it keeps one vector per token and matches each word of the query to the closest word in each card (the late interaction primer on this site draws the mechanism).

So the server runs mLateOn, and its tool description tells the agent to write queries the way card text is worded. It searches all 34,646 cards exactly, one matrix product per query, because at this size an approximate index buys nothing. The Docker image returns exactly the same top 10 as the benchmark reference on every query, in 130 to 340 ms. It has three read-only tools, search_cards, get_card and find_similar, with five filters.

One lesson cost more runs than the engine did. The agent searches only when it is told when to. Offered the tools with no cue, Sonnet made zero tool calls in 42 deck tasks and answered from memory. Each tool description now opens with Before recommending cards for a deck, call this to find candidates instead of listing them from memory. With that sentence the agent searched in 25 of 30 tasks on the tuning decks; without it, in 10 of 30.

Automatic lists of correct cards are incomplete, so both agent benchmarks also use a grader: a separate Claude model that grades cards blind, 15 per call, in random order. It never sees which agent proposed a card and never sees any popularity data. Hidden random cards are mixed into every run to check that it does not accept everything. The two graders look for different things:

  • The relevance grader sees the request with its constraints and each card's rules text. 2 = does what was asked and meets every constraint; 1 = a weaker or narrower version a player might still consider; 0 = does not do it, or breaks a constraint. It accepted 1 of 160 hidden random cards and graded 98.9% of the cards already on the lists relevant.
  • The deck-fit grader sees the deck (the commander's rules text with its name hidden, plus the other 99 card names) and each proposed add. 2 = a clear upgrade: it supports the commander or the deck's plan, or fills a role the deck is short of (ramp, card draw, removal, interaction), and beats the deck's weakest cards; 1 = a reasonable but low-priority upgrade; 0 = no specific reason to be in this deck. It is told not to reward a card for being widely played. On the test decks it accepted 10 of 84 hidden random legal cards and none of 42 cards already in the deck.

05One answer key is not enough

Every automatic answer key has a blind spot. The tag and pattern lists miss cards that do the job in other words: 22 to 23% of each agent's top-10 cards were graded relevant but were missing from the lists. The patterns also reward exactly the wording grep can rebuild. Player add rates have a different blind spot. They reward what many players add, and that means popular cards. A deck can also be improved in many different ways.

On the same adds, the two ways of scoring disagree. The deck-fit score shows a clear gain, better on 13 of 14 decks, and it holds on rule-abiding adds alone (0.52 against 0.67). The match with player add rates is not significant. The reason is popularity. With mtg-search the agent's typical add is around the 1,000th most-played card on EDHREC, against the 300th from memory, and player add rates favour the most-played cards. The deck-fit grader shows no such pull: if anything, its top grades went to less popular cards. In the swap task the deck-fit gain was smaller and not significant.

So every test set is scored two ways, by an automatic list and by a grader with hidden random cards. Where the two disagree, the disagreement is the finding.

06Where it stops

34,646 cards and 3.1M tokens of text is a small corpus. A grep over it takes a fraction of a second, and a strong agent can page through the matches. Grep also had a second advantage: Sonnet knows Magic's rules-text templating by heart, so it writes patterns that hit. Even so, grep matched search's relevance only with a prompt that describes the card file, and then it used twice the tokens, because its matches come unranked, in file order.

That cost scales with the corpus. More documents mean more matches per pattern to page through, while ranked search still returns the best ten. In a larger collection, or one whose wording the model has not memorised, I expect the token gap to widen and the quality gap with it. I have not measured that. Read the grep result as the best case for having no search infrastructure: a small corpus, a model that knows its wording, and a prompt tuned to the file. Search needed none of that here.

The limits I know of. Every agent result is one run per task, and the share of tasks in which the agent chooses to search swings by 20 points between identical runs. The graders are the same model family as the agent, so a grader from another family is the check I would add next; it needs API budget this hobby project does not have. The deck-fit criteria went through three versions on the tuning decks before any test deck was graded, and shown an anonymised deck, the grader still named 12 of 15 of them. The 14 test decks have been used for more comparisons than I would like, and fresh ones become usable when players' data on them matures.

07The data

The server, the benchmarks and every run record are in private repositories for now, and the reason is licensing rather than modesty. The card data is Scryfall's, and their terms forbid republishing it. The deck labels come from EDHREC, collected with permission for private evaluation only. The three datasets are versioned on Hugging Face so the numbers above can be traced to a fixed revision:

  • mtg-search-index, revision scryfall-20261014090155: the 34,646 cards, tags, rulings and the mLateOn embeddings the server searches.
  • mtg-search-bench, v1.0: the 363 benchmark queries, the 113 agent tasks, 2,799 relevance grades and the final relevance labels. The step-two numbers in Figure 2 recompute exactly from it.
  • mtg-precon-bench, v1.0: the precon decklists, the EDHREC add and cut rates, and 2,385 deck-fit grades.

The search benchmark holds only my own queries, tasks and grades, keyed by card id, so it is the one that could be released.
