Learned sparse retrieval

Search, with the vectors showing

This page searches everything on the site — papers, slides, projects, the CV — using inference-free SPLADE. No model runs in your browser. Not a quantized one, not a small one: none. The reason is worth a minute, because it is the whole trick.

SPLADE is asymmetric. Encoding a document is a 67-million-parameter masked language model's job: it reads the passage and outputs a weight for every one of the 30,522 tokens in BERT's vocabulary, of which all but a hundred or so come out at exactly zero. That vector is sparse, and — unlike a dense embedding — every non-zero dimension has a name you can read.

Encoding a query, in the inference-free variant, is not a model at all. It is a tokenizer and a lookup table: one static weight per vocabulary token, learned once during training and shipped as a text file. So the expensive half runs offline, in tools/build_search_index.py, and what the browser downloads is that table, the vocabulary, and the postings. Scoring is a sparse dot product — six lines of JavaScript.

Which means this page can do semantic-ish retrieval on GitHub Pages with no inference server, no ONNX runtime, no WASM, and no model download. And because the dimensions are vocabulary tokens, the machinery can be put on screen instead of described. That is what the panels below do: they show you the vector, the query's decomposition, and exactly which terms produced each score.

These filters are ordinary metadata matching, and they run after scoring — the model never sees a year or a venue. That is deliberate. SPLADE shreds exactly the strings academic search leans on: ICUAS becomes ic ##ua ##s, surnames become subword confetti, and version numbers lose their meaning. Learned sparse retrieval is for meaning; for a known-item lookup you want matching, so both are here, kept visibly apart.

    The honest caveats

    The query weights are static MS MARCO term weights — essentially a learned IDF, fixed at training time. They know that drone is more discriminative than system in general; they know nothing about this corpus in particular. On 78 passages that is fine, and it is why no model is needed at query time. On a real collection you would want the corpus statistics too.

    The model is English-only, and it is a document expander, not a reasoner: it will happily add rescue to a passage about search and rescue, and it will not notice that Grøntved is a name. Ask it for a person or a venue and you will get subword noise — use the filters, or the pages themselves.

    Everything here is built by tools/build_search_index.py from OpenSearch's inference-free sparse encoder (Apache-2.0), re-run by CI whenever the content changes. The client is search/splade.js: a WordPiece tokenizer and a dot product, no dependencies.

    If sparse vectors with named dimensions are interesting to you, the adjacent idea is late interaction, which keeps one dense vector per token instead of collapsing to one per document — a different answer to the same complaint about single-vector search. There is a primer on it here.
